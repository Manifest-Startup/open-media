# ADR 0042: One sign-in gateway, passkey-first sign-in and MFA

- Status: **accepted; built, not deployed** (2026-11-16). Spec: [SIGN_IN_GATEWAY.md](../SIGN_IN_GATEWAY.md). Builds on [ADR 0027](0027-one-agent-plugin-for-every-marketplace.md) ("Sign in with Open Media"), [ADR 0034](0034-passwords-and-passkeys.md) (passwords and the passkey second step) and [ADR 0041](0041-app-integrations.md) (app integrations).

## Context

Open Media is the identity provider for its own web app, for AI hosts on `/account/mcp` and for web apps such as Manifest on `/v1/connected`. Until now the account OAuth flow had its own plain Worker HTML pages (an email form, a code form and a link page), while the web app had a different sign-in screen. Passkeys existed only as a second step after a password or email code (WebAuthn MFA, ADR 0034).

## Decision

1. **One page: `openmedia.site/signin`** (`src/ui/SignInGateway.tsx`, lazy-loaded; `App.tsx` routes it on the web only). Order: **Continue with passkey** (also offered in the email field's autofill where the browser supports conditional UI), then email (a one-tap link and a code), then a password behind a quiet link. New accounts choose a name and handle on the same page, and in own mode are offered "Add a passkey" once. Light and dark, 375 px to desktop, the app's own design system.
2. **Two modes.**
   - *Own mode* (no `request`): the web app's sign-in, with the saved Supabase client. The web app's "Sign in" buttons, a pending second step, and a signed-out visit to `/settings/security` go here; it returns to `next` (a same-site path only). The phone apps keep their native sign-in screen.
   - *App mode* (`?request=<challenge>`): `/authorize` for account scope stores the challenge in KV, sets the `om_account_oauth` cookie (path `/authorize`, HttpOnly, Secure, SameSite=Lax) and **302s to the gateway**. The gateway reads the app's name and icon from `GET /authorize/account/request` (public fields only, CORS for the gateway origin), signs in with a **separate in-memory Supabase client** (implicit flow, nothing persisted), shows a short consent list and **Continue to <App>**, and makes a top-level form POST of `{challenge, access_token, refresh_token}` to `POST /authorize/account/session`.
3. **`/authorize/account/session` checks**, in order: body size; `Origin` is the API or the gateway; the cookie equals the challenge and the challenge exists in KV; the per-IP attempt limit; the access token is a JWT that Supabase `/auth/v1/user` accepts; `open_media_session_meets_mfa()` is true for that token. Then `completeAuthorization` (props: the session, as before), the challenge is deleted, the cookie cleared, and the person is sent to the app's `redirect_uri`.
4. **The one-tap email link** still returns through `/authorize/account/link`, which checks the cookie and 302s to the gateway with `token_hash`; the gateway asks ("Finish signing in") before `verifyOtp({ token_hash, type })`, so link scanners can't use it. **The old Worker forms (`/authorize/account/email`, `/authorize/account/complete`, the code and link pages) and `verifySignInLink` are removed**: a no-JS fallback would have duplicated every check for no real audience (the web app needs JavaScript anyway).
5. **Second step.** Once a person has a verified factor, the database requires it (ADR 0034's three layers). `open_media_session_meets_mfa()` now also says, explicitly, that a verified TOTP factor counts, and accepts a **passkey-first sign-in** for people whose second step is a passkey (see below). The gateway asks **Confirm it's you**: passkey (WebAuthn MFA), the authenticator code, or **Use a recovery code**. The phone apps' native second-step screen gained the authenticator-code field, so a TOTP account can still sign in there.
6. **Recovery codes**: 10 codes of 16 characters (80 random bits) from `open_media_new_recovery_codes()`, which needs a full session and stores only SHA-256 hashes (salted with the user id) in `app_private.recovery_codes`, not reachable through the API. Regenerating replaces all. `POST /v1/auth/recovery` takes the person's own aal1 session: the Worker checks the token's signature (not its second step), uses up the code with the service key (`open_media_use_recovery_code`, at most five wrong codes per person per 15 minutes), then deletes the person's MFA factors with the admin API (`SUPABASE_SECRET_KEY`). The same session is then fully signed in, and the gateway tells the person to set a second step up again. Sign-in passkeys are kept.
7. **Sign-in and security** (Profile, web): passkeys (Supabase `/passkeys`: list, add, rename, remove); the ADR 0034 second-step passkey; an authenticator app (QR code drawn by the lazily loaded `QrGrid` with the existing `qrcode` package, plus the setup key; verify; remove); recovery codes (make, download as a text file, count left); password; **apps signed in with Open Media** (`GET /v1/me/apps` and `DELETE /v1/me/apps/{grantId}`, the OAuth provider's `listUserGrants` and `revokeGrant` for the person; refused over `/v1/connected`). `openmedia.site/settings/security` opens this section.
8. **`/v1/me` and `/v1/connected/me`** also return `email`, `email_verified` and `has_profile`. Over `/v1/connected/me` a new account gets `has_profile: false` instead of a 404; `/v1/me` with the person's own token keeps `no_profile`.
9. **Page security.** `/signin` gets its own CSP: scripts from the site only (no analytics), no frames, `connect-src` only the Supabase project and `api.<site>`, `form-action 'self' https:` (the POST is followed by a redirect to the app's https callback, and browsers check that redirect against `form-action`), `no-store`. The passkey relying party is `openmedia.site`. Tokens are never logged, never put in the address bar, and one-time values (`token_hash`, `code`) are removed from it as soon as they are read.
10. **CIMD changes.** The provider caches each Client ID Metadata Document in the Workers Cache API for as long as the document's own `Cache-Control` allows (at most 7 days, not at all with `no-store`/`no-cache` or no `max-age`). When `/authorize` no longer matches the cached copy (for example a new `redirect_uri`), the Worker removes that entry and parses the request once more, so a changed document is read again at once.

## What a passkey-first sign-in gets (verified)

Verified 2026-11-16 on the local stack (Supabase CLI 2.114, GoTrue v2.195, `[auth.passkey] enabled = true`): registering a passkey through `/auth/v1/passkeys/registration/*` and signing in through `/auth/v1/passkeys/authentication/*` (Chrome virtual authenticator, user verification on) gives a session with **`aal: "aal1"`** and **`amr: [{"method": "passkey"}]`**. Passkeys live in `auth.webauthn_credentials`, not in `auth.mfa_factors`, so adding one does not turn on a second step. For comparison: an email code gives `aal1` / `otp`, a password `aal1` / `password`, and the authenticator code after an email code `aal2` / `totp, otp`.

So `open_media_session_meets_mfa()` is true when the session is `aal2`, or the person has no verified factor, or the JWT's `amr` contains `passkey` **and** the person has no verified TOTP factor. A passkey sign-in is phishing-resistant and checks the person, so it stands in for a passkey second step; it does not stand in for an authenticator app, so TOTP users still enter their code. GoTrue itself still sees such a session as `aal1`, so a change it guards with aal2 (removing a verified factor) asks the person to confirm with their second-step passkey first.

## Consequences

- Every sign-in for Open Media and connected apps looks and behaves the same, and the API never sees a password or passkey.
- The grant's session is separate from the web app's, so refreshing one never signs the other out.
- `has_profile` and `email_verified` let apps such as Manifest link accounts by verified email without a second request.
- The Worker needs `SUPABASE_SECRET_KEY` for recovery codes (already set by the owner's script for webhooks).
- Production needs Supabase Auth settings that only the owner can change (below).

## Production (owner)

`~/.config/manifest/enable-open-media-email.sh` now also sets, through the Management API: `webauthn_rp_id=openmedia.site`, `webauthn_rp_origins=https://openmedia.site,https://www.openmedia.site`, `webauthn_rp_display_name=Open Media`, `mfa_web_authn_enroll_enabled`, `mfa_web_authn_verify_enabled`, `mfa_totp_enroll_enabled`, `mfa_totp_verify_enabled`, `mailer_autoconfirm=false` (email confirmations on), `password_min_length=8`, the redirect allow list entries `https://openmedia.site/signin**` and `https://api.openmedia.site/authorize/account/link**`, and (tolerantly, since Supabase calls passkeys experimental) `passkey_enabled=true`. The names were checked against the Supabase CLI 2.114's own `config push` mapping (for example `_.passkey_enabled=T.passkey.enabled`, `_.webauthn_rp_origins=T.webauthn.rp_origins.join(",")`, `_.mailer_autoconfirm=!T.email.enable_confirmations`, `_.password_min_length=T.minimum_password_length`). Production web builds now default to `SIGN_IN_EMAIL_CODES=1`, because the send-email hook (ADR 0041) puts a code in every email.

## Verification (2026-11-16, local stack)

- **Web, own mode** (Chrome, virtual authenticator): a new synthetic account signed up with an email code, chose a name and handle, added a passkey from "Sign in faster next time", forgot its session, and signed in again with **Continue with passkey** only (`aal1`, `amr` passkey, same user). Then in Sign-in and security: set up an authenticator app from the QR code's key, made 10 recovery codes; a later email-code sign-in asked **Confirm it's you** and the TOTP code gave `aal2`. A wrong recovery code was refused; a right one (typed in capitals with spaces) signed in, removed the factor, and left 9 codes.
- **Web, app mode**: the full Worker under `wrangler dev` with its OAuth provider and local KV, a synthetic dynamically registered client and a web build pointed at it. `/authorize` set the cookie and redirected to the gateway; the app's name showed and the email was pre-filled from `login_hint`; a new account signed in with the emailed code, made its profile, saw the consent list, and **Continue** returned to the client's callback with `code` and `state`. The token exchange gave `scope account`; `/v1/connected/me` answered `has_profile: true`, the email and `email_verified: true`; no Supabase session was saved in the browser. `GET /v1/me/apps` listed the app, `/v1/connected/me/apps` answered 403, and `DELETE /v1/me/apps/{id}` made the app's token answer 401.
- **Screens**: sign-in, password, code, second step, recovery, profile and consent at 375 px and 1280 px, light and dark.
- **iOS Simulator** (iPhone 17 Pro, debug build on local Metro): the native sign-in screen is unchanged; a synthetic account with an authenticator app signed in with its password, got the native **Confirm it's you** screen with the new code field, and reached the feed. Sign-in and security renders on the phone (passkeys point to the web).
- Unit tests for the gateway rules, the session POST, the challenge hand-offs, CIMD eviction, recovery codes, `/v1/me` fields, the CSP and the web routes; pgTAP tests for the MFA rule and recovery codes.

Not verified: Android (the Mac has JDK 11; Android needs 17+); Safari and Firefox; real Touch ID, Face ID or security keys; conditional UI (autofill) in a real browser profile; the one-tap email link in app mode end to end (the local stack has no send-email hook, so it was covered by unit tests); production, which needs the deploy, the migration and the owner's script.
